# 容量规划与内存模型

cache-cat 是“全内存 + Raft 复制”的状态机，不是带淘汰策略的缓存。本文说明内存都花在哪里、
如何估算单节点容量，以及为什么“加节点”不等于“加数据容量”。

## 1. 一个节点存什么

每个 Raft 成员都会把完整日志应用到自己的状态机。当前没有内建分片/分区，因此每个节点
保存的是**全量数据**，不是 `数据量 / 节点数`。

进程内存主要包括：

- 存活的 key 与 value；
- 每条记录的元数据（版本号、过期时间、容器节点/桶）；
- hash/tree/skiplist 索引与 allocator 碎片；
- Raft apply 缓冲、在途请求、客户端连接缓冲；
- 快照构建与增量快照队列的临时内存。

Raft 日志与快照还会占用磁盘；这部分不属于内存状态大小，但同样要纳入主机容量规划。

## 2. 没有淘汰，也没有 maxmemory

cache-cat 没有 LRU/LFU 淘汰，也没有 `maxmemory` 兜底。数据量超过进程内存预算时，进程会被
OOM killer 杀掉或分配失败，**不会静默删除 key**。

如果业务允许数据随时丢弃并从源站重新加载，应该使用 Redis/Valkey；如果要求写入成功后，
即使单节点故障数据仍然是集群一致状态的一部分，才是 cache-cat 的场景。

## 3. 容量估算公式

下面只是起点，不是精确的 allocator 模型：

```text
单节点内存
  >= 实际数据量
   × 开销系数（大致 1.5x - 3x，小 key 更多）
   + 快照峰值余量
   + Raft/连接/allocator 余量
   + 20% - 30% 操作系统余量
```

开销系数取决于 key/value 大小、数据类型（stream、zset、hash、PEL）、过期元数据和碎片。
小 key 的相对开销远高于大 value。

快照构建会序列化数据集，可能在存活数据之上临时增加一大块分配；见 `snapshot_zh.md`。
容器/主机的内存上限要按快照峰值规划，而不是只按稳态数据量。

`MEMORY USAGE` 是逻辑容器的估算，不是整个进程 RSS。主机容量应结合 `INFO memory`
（`used_memory_rss`、`used_memory_peak_rss`）和真实压测校准。

## 4. 扩展与部署

- **增加节点提升的是容错与复制能力，不是数据容量。** 每个节点仍然保存全量数据。
- 要突破单节点内存上限，需要外部做分片，或拆成多个 Raft group；当前仓库没有内建分片。
- 应把 cache-cat 当作专用的内存优化型数据节点，避免和其他内存大户混部。
- 副本应跨主机/故障域反亲和部署，避免一台主机故障同时带走所有副本。
- 容器内存上限要高于最坏情况下的快照峰值，并保留 OS 余量；否则会被 OOM kill。

## 5. 实测示例

`benchmark_ycsb_zh.md` 中的官方 YCSB 测试在 30 GiB 主机上加载了 1,000,000 条约 1 KB
的记录。原始 payload 约 1 GB，测试后服务端进程 RSS 约 3 GB。这个倍数来自分配器、元数据、
索引、Raft 缓冲和保留内存等因素，不是通用倍率。

规模放大后同样成立：1 亿条 1 KB 记录，**每个副本**仅原始 payload 就约 100 GB，还不含开销
和快照余量。这需要大内存主机或分片，而不是简单地多加几个节点。

## 6. 实践检查清单

- 用真实数据规模估算原始大小与开销系数；
- 加上快照峰值和 20% - 30% 的 OS 余量；
- 监控 `INFO memory` 的 RSS 和主机内存压力；
- 压测使用真实的 key/value 大小和数据结构，不要只测小字符串；
- 需要弹性容量和淘汰策略时选择 Redis/Valkey；
- 需要强一致全量副本时，每个节点都按全量数据规划。
